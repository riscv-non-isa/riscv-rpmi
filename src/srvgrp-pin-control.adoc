===  Service Group - PIN_CONTROL (SERVICEGROUP_ID: 0x0011)
This service group is used to discover and control the pins (or pads) of the
system. Services defined in this group are used to enumerate pins, groups of
pins, and pin functions, to select the function performed by a pin or a group
of pins, and to set or get the electrical configuration of a pin or a group
of pins.

A pin is a physical interface of the system to the outside world. Since the
number of pins in a system is limited, a pin is generally multiplexed and can
perform one of several functions at a time. A function represents a specific
role which a pin or a set of pins can perform, for example, the clock and data
signals of an I2C interface or a general purpose input/output (GPIO).

A function may provide GPIO capability which is indicated in the function
attributes. Once a GPIO capable function is enabled on a pin or a group, the
application processor can control the direction of a pin using the
`INPUT_MODE` and `OUTPUT_MODE` configuration types, drive the pin level using
the `OUTPUT_VALUE` configuration type, and read the pin level using the
`INPUT_VALUE` configuration type. The configuration types are listed in
<<pinctrl-config-types>>. The application processor can discover the GPIO
capable functions of a pin by retrieving the functions of the pin through
the `PINCTRL_GET_PIN_ASSOCIATIONS` service and then checking the GPIO
capability flag of each function through the
`PINCTRL_GET_FUNCTION_ATTRIBUTES` service.

The platform may support access control for pins and groups through
permissions and ownership. Permissions control which clients of the system
are allowed to access a pin or a group. A client can read its own access
permission through the `PINCTRL_GET_PERMISSIONS` service, and a trusted
client can allow or deny access for the clients of the system through the
`PINCTRL_SET_PERMISSIONS` service. Ownership provides exclusive control of a
pin or a group at runtime. A client can claim exclusive control through the
`PINCTRL_REQUEST` service and release it through the `PINCTRL_RELEASE`
service. While a pin or a group is claimed, it is unavailable to all other
clients. Permissions define whether a client may access a pin or a group,
whereas ownership defines which client is currently using it.

These services are optional. During initialization, the application
processor must first discover the implemented services through the
`PINCTRL_GET_ATTRIBUTES` service. It can then check its access permissions,
claim exclusive control of the pins and the groups it needs, and configure
them.

[#pinctrl-pin-organization]
==== Pin Organization
Pins which together enable a specific function are arranged in a group. A
group contains one or more pins, and the same function is enabled on all
pins of a group at once. A group which contains only one pin is referred to
as a single-pin group. A function which requires only a single pin and is
enabled directly on individual pins without any group is referred to as a
single-pin function. The single-pin property describes the number of pins
which the function requires, and not the number of functions which a pin
can perform.

A platform may expose functions at two granularities. At the signal
granularity, each function represents a single signal (for example
`i2c0_sda` or `i2c0_scl`) and is a single-pin function which is enabled
directly on a pin. The I2C interface requires both signals to operate, but
each signal function requires only its own pin, which is what makes it a
single-pin function. At the peripheral granularity, a function represents a
complete peripheral interface (for example `i2c0`) and is enabled on a group
which contains all pins of that peripheral. A platform may expose either
granularity or both. For example, the pads `gpio0_0` and `gpio0_1` can form
the group `i2c0`, where each pad individually performs the single-pin
functions `i2c0_sda` and `i2c0_scl` respectively, and the platform may
additionally expose the peripheral function `i2c0` which is enabled on the
group `i2c0` to enable both signals in a single request. Irrespective of the
function granularity, a group can always be used to discover its pins and to
apply a configuration to all of its pins in a single request.

A function may be supported by multiple groups, but a function must not be
enabled through more than one group at a time. A pin may be part of multiple
groups since a pin can serve multiple functions through multiplexing. The
application processor must not request the platform microcontroller to enable
different functions on overlapping groups, and the platform microcontroller
must not enable a function on a group when one or more pins of that group are
already in use by another function.

A platform can expose the pin mapping of a function through two mechanisms.
With fixed mapping, the function is enabled through groups, and each group
is a fixed set of pins. With flexible mapping, each signal of the function
is a single-pin function which can be enabled on any of its candidate pins.
A platform may use either mechanism or both.

For example, a QSPI interface which requires four data pins, one clock pin,
and one chip enable pin is exposed as a function `qspi0` which is enabled
through a group of six pins. If the platform can route the QSPI interface
to two different sets of pads, then the platform exposes two groups, for
example `qspi0_a` and `qspi0_b`, and the `PINCTRL_GET_FUNCTION_GROUPS`
service returns both groups for the function `qspi0`. The application
processor enables the function through the group of its choice.

The platform does not need to define a group for every possible combination
of pins. When the pin choices are flexible, for example when many pins can
each select one of many functions, the platform exposes each signal as a
single-pin function. The `PINCTRL_GET_FUNCTION_GROUPS` service returns the
candidate pins of each single-pin function, the
`PINCTRL_GET_PIN_ASSOCIATIONS` service returns the candidate functions of
each pin, and the application processor enables each signal on the pin of
its choice. Groups are recommended for fixed or common pin mappings, and
single-pin functions are recommended for flexible pin mappings.

Whether a function uses fixed or flexible mapping is indicated by the
single-pin function flag returned by the `PINCTRL_GET_FUNCTION_ATTRIBUTES`
service. For a single-pin function, the `PINCTRL_GET_FUNCTION_GROUPS`
service returns pin IDs instead of group IDs, and the `PINCTRL_SET_FUNCTION`
service enables the function on a pin instead of a group.

Each pin is identified by a `PIN_ID`, each group by a `GROUP_ID`, and each
function by a `FUNCTION_ID`. These are separate identifier spaces, and each
identifier is a 32-bit integer which is sequential and starts from `0`.

The services of this service group reference a pin, a group, or a function
only through its numeric identifier. Pins, groups, and functions also have
names which are NULL-terminated ASCII strings up to 32-bytes. Names are
informational and implementation defined, and the platform may choose any
naming scheme. The recommended naming convention is:

* Pin names identify the physical pad of the system, for example the pad
  name defined in the system datasheet such as `gpio0_0`, and should not
  encode a function which the pin can perform.
* Function names match the signal or the function performed. Signal level
  functions are named after the signal, for example `i2c0_sda` or `uart0_tx`.
  Peripheral level functions are named after the peripheral instance, for
  example `i2c0`.
* Group names match the peripheral instance whose pins they contain, for
  example `i2c0` or `uart0`.
* Function and group names which provide GPIO capability should include
  `gpio` in the name, for example `gpio0_0`.

The organization of pins into groups and functions is implementation
defined. The recommended organization strategy is:

* Define a group for each set of pins which operate together, such as the
  pins of a peripheral interface. Define one group for each supported pin
  mapping when the mappings are fixed.
* Define single-pin functions for signals which can be routed to many pins,
  instead of defining a group for every possible combination of pins.
* Define a single-pin GPIO function for each pin which the application
  processor can control directly.
* Deny access to the pins and the groups which are reserved for the
  platform through the access permissions.

[#pinctrl-config-types]
==== Pin Configuration Types
The configuration of a pin or a group is expressed as a list of configuration
type and configuration value pairs. The following table lists the standard
configuration types and the encoding of their corresponding configuration
values. The platform microcontroller must apply the configuration according
to the configuration value. For configuration types with enable/disable
semantics, the configuration value `0` must disable the configuration and the
configuration value `1` must enable it.

The supported values of a configuration type for a particular pin or a
group are platform specific. The application processor can discover them
through the optional `PINCTRL_GET_SUPPORTED_CONFIG_VALUES` service, or
through hardware description mechanisms such as device tree or ACPI.

==== Service: PINCTRL_GET_FUNCTION_ATTRIBUTES (SERVICE_ID: 0x05)
This service provides the attributes of a function, including the number of
groups which can enable the function and its name, represented as a 32-byte
array of ASCII strings.

If the function is a single-pin function, then the `NUM_GROUPS` field returns
the number of pins which can enable the function directly.

The single-pin function flag and the GPIO capability flag returned in the
`FLAGS` field are independent attributes of a function. The single-pin
function flag describes how the function is enabled, either directly on
individual pins or through groups. The GPIO capability flag describes
whether the application processor can control the direction and the level of
the pins once the function is enabled. All combinations of the two flags are
valid. The <<table_pinctrl_function_flags_examples>> below shows an example
for each combination.

==== Service: PINCTRL_GET_GROUP_PINS (SERVICE_ID: 0x06)
This service is used to get the list of pins in a group. The message can pass
the `PIN_INDEX` which is the index to the first pin ID to be described in the
returned pin ID array. If all pin IDs are required, then this index value can
be `0`.

If the total number of words required to store all pin IDs of the group
exceeds the available words in the message DATA field, then the platform
microcontroller will return the pin IDs which can be accommodated in one
message and set the `RETURNED` field to the number of pin IDs returned and
the `REMAINING` field to the number of remaining pin IDs.

When the `REMAINING` field is not `0`, the application processor must call
this service again with the appropriate `PIN_INDEX` set to get the remaining
pin IDs.

words in the message DATA field, then the platform microcontroller will
return the IDs which can be accommodated in one message and set the
`RETURNED` field to the number of IDs returned and the `REMAINING` field to
the number of remaining IDs.

When the `REMAINING` field is not `0`, the application processor must call
this service again with the appropriate `GROUP_INDEX` set to get the
remaining IDs.

along with the group through which each function is enabled. Each entry in
the returned array is a pair of `FUNCTION_ID` and `GROUP_ID` words. If the
function is a single-pin function which is enabled directly on the pin, then
the `GROUP_ID` word of the pair is set to `0xFFFFFFFF`.

For example, if the pin `gpio0_0` can perform the single-pin function
`pwm0` directly and the peripheral function `i2c0` through the group
`i2c0`, then this service returns two pairs: one with the function ID of
`pwm0` and the `GROUP_ID` word set to `0xFFFFFFFF`, and one with the
function ID of `i2c0` and the group ID of the group `i2c0`.

The message can pass the `ASSOCIATION_INDEX` which is the index to the first
pair to be described in the returned array. If all pairs are required, then
this index value can be `0`.

If the total number of words required to store all pairs exceeds the
available words in the message DATA field, then the platform microcontroller
will return the pairs which can be accommodated in one message and set the
`RETURNED` field to the number of pairs returned and the `REMAINING` field to
the number of remaining pairs.

When the `REMAINING` field is not `0`, the application processor must call
this service again with the appropriate `ASSOCIATION_INDEX` set to get the
remaining pairs.

==== Service: PINCTRL_GET_SUPPORTED_CONFIG_VALUES (SERVICE_ID: 0x0E)
This service is used to get the values of a configuration type which are
supported by a pin or a group. For example, this service can return the
drive strength values supported by a pin.

This service is optional. The application processor can discover whether
this service is implemented through the `FLAGS` field returned by the
`PINCTRL_GET_ATTRIBUTES` service. If this service is not implemented, then
the supported values must be discovered through hardware description
mechanisms such as device tree or ACPI.

The supported values are returned either as a discrete list of values or
as a linear range. The linear range is returned as three words which are
the minimum value, the maximum value, and the step between two successive
values. The value format flag in the `FLAGS` field of the response
indicates the format of the returned values.

The message can pass the `VALUE_INDEX` which is the index to the first
value to be described in the returned array. If all values are required,
then this index value can be `0`. For the linear range format, the
`VALUE_INDEX` must be `0`.

If the total number of words required to store all values exceeds the
available words in the message DATA field, then the platform
microcontroller will return the values which can be accommodated in one
message and set the `RETURNED` field to the number of values returned and
the `REMAINING` field to the number of remaining values.

==== Service: PINCTRL_GET_CONFIG (SERVICE_ID: 0x0F)
This service is used to get the configuration of a pin or a group, and the
function currently enabled on the pin or the group.

The `MODE` field selects the data to be returned. If `MODE` is `0`, then only
the configuration value of the configuration type passed in the
`CONFIG_TYPE` field is returned and the `RETURNED` field is set to `1`. If
`MODE` is `1`, then the configuration values of all configuration types
supported by the pin or the group are returned in numerically increasing
configuration type order. If `MODE` is `2`, then no configuration values are
returned and only the `SELECTED_FUNCTION` field is valid, with the
`RETURNED` field set to `0`.

configuration type and value pairs exceeds the available words in the message
DATA field, then the platform microcontroller will return the pairs which can
be accommodated in one message and set the `RETURNED` field to the number of
pairs returned and the `REMAINING` field to the number of remaining pairs.
When the `REMAINING` field is not `0`, the application processor must call
this service again with the appropriate `CONFIG_INDEX` set to get the
remaining pairs.

==== Service: PINCTRL_SET_CONFIG (SERVICE_ID: 0x10)
This service is used to set the configuration of a pin or a group. The
service allows multiple configurations to be set in a single request through
an array of configuration type and value pairs.

If the total number of words required to store all configuration type and
value pairs exceeds the available words in the message DATA field, then the
application processor must send multiple requests. The `FLAGS` field must
have the final request flag set to `1` in the last request of such a sequence
and set to `0` in all preceding requests. If all pairs fit in a single
request, then the final request flag must be set to `1`.

If this service fails, then the configurations already applied by previous
requests of the sequence and by the preceding pairs of the failing request
remain applied. The platform microcontroller does not revert previously
applied configurations.
